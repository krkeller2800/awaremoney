# Purchase Analytics Implementation Plan

## Goal

Add privacy-preserving purchase analytics after the current DEBUG-only local diagnostics have proven useful. The first production analytics pass should answer whether users see the paywall, tap purchase, encounter StoreKit failures, cancel, restore, or purchase successfully without collecting financial data or requiring a paid analytics database.

## Cost-Free Hosting And Database Choice

Use the existing Cloudflare-maintained `komakode.com` infrastructure:

- Cloudflare Pages for a simple internal HTML dashboard.
- Cloudflare Workers or Pages Functions for JSON ingestion and JSON reporting endpoints.
- Cloudflare D1 as the primary analytics database because it has a Free plan with small SQLite-style relational storage.

Do not use Workers Analytics Engine as the primary database for this pass. It is useful for high-volume event analytics, but Cloudflare currently describes pricing as not yet billed and shared ahead of future billing. That makes D1 a better fit for the requirement that the analytics database stay cost free.

Current Cloudflare constraints to design around:

- Workers Free plan has a daily request quota.
- Pages Functions requests count against the Workers Free quota.
- D1 Free plan has limited database count, storage, and per-invocation query limits.
- Free-tier limits can change, so verify Cloudflare pricing/limits before implementation and before each release that depends on analytics.

## Privacy Rules

Do not send:

- Account names.
- Payees.
- Transaction amounts.
- Balances.
- Imported document names.
- User-entered financial text.
- Apple ID, email, name, or other direct identity.
- Raw assistant prompts or responses.

Allowed event fields:

- Anonymous install ID generated by the app and stored locally.
- App version and build.
- Platform and OS major/minor version.
- Event name.
- Paywall source.
- StoreKit product load state.
- StoreKit product ID hash or short code, not the full product ID unless needed for debugging.
- Timestamp generated server-side.
- Coarse locale or storefront country only if needed for StoreKit reliability.
- Debug/test flag when events come from debug, sandbox, or TestFlight builds.

The anonymous install ID must not be derived from device identifiers, Apple ID, financial data, or account data. Use a random UUID generated on first launch. Provide a Settings toggle to disable analytics before any production analytics release.

## Events To Track

Start narrow. Track only purchase-funnel and reliability events:

- `paywall_impression`
  - `source`
  - `app_version`
  - `build`
  - `premium_active`
- `purchase_button_tap`
  - `source`
  - `product_load_state`
- `purchase_result`
  - `source`
  - `result`: `success`, `cancelled`, `pending`, `unverified`, `failed`
- `product_load_result`
  - `result`: `loaded`, `empty`, `failed`
  - `storefront_country` when available
- `restore_tap`
  - `source`
- `restore_result`
  - `result`: `restored`, `none_found`, `failed`

Do not add broad navigation analytics in this pass.

## D1 Schema

Use one append-only events table first. Aggregates can be derived with SQL.

```sql
CREATE TABLE purchase_events (
    id TEXT PRIMARY KEY,
    received_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    install_id_hash TEXT NOT NULL,
    session_id TEXT,
    event_name TEXT NOT NULL,
    paywall_source TEXT,
    purchase_result TEXT,
    product_load_result TEXT,
    product_load_state TEXT,
    storefront_country TEXT,
    app_version TEXT,
    build_number TEXT,
    platform TEXT,
    os_version TEXT,
    channel TEXT NOT NULL DEFAULT 'production'
);

CREATE INDEX idx_purchase_events_received_at ON purchase_events(received_at);
CREATE INDEX idx_purchase_events_event_name ON purchase_events(event_name);
CREATE INDEX idx_purchase_events_source ON purchase_events(paywall_source);
```

Hash `install_id` before storage using a server-side secret pepper so the database never stores the app-generated UUID directly.

## Cloudflare Endpoints

Host under `komakode.com`, preferably as either `/api/debtscope/purchase-events` or an analytics subdomain such as `analytics.komakode.com`.

### JSON Ingestion

`POST /api/debtscope/purchase-events`

Request body:

```json
{
  "installId": "random-app-generated-uuid",
  "sessionId": "optional-session-uuid",
  "eventName": "paywall_impression",
  "paywallSource": "settings",
  "purchaseResult": null,
  "productLoadResult": null,
  "productLoadState": "loaded",
  "storefrontCountry": "US",
  "appVersion": "1.0",
  "buildNumber": "42",
  "platform": "iOS",
  "osVersion": "18.5",
  "channel": "testflight"
}
```

Response:

```json
{
  "ok": true
}
```

Validation rules:

- Reject unknown event names.
- Reject unknown paywall sources.
- Cap string lengths.
- Ignore extra fields.
- Do not accept arbitrary JSON blobs.
- Rate-limit by IP and hashed install ID.
- Return success for analytics-disabled or malformed optional fields only when no useful debugging would be lost.

### JSON Reporting

`GET /api/debtscope/purchase-summary?days=30`

Response:

```json
{
  "days": 30,
  "paywallImpressions": 120,
  "purchaseButtonTaps": 18,
  "successfulPurchases": 3,
  "cancelledPurchases": 9,
  "productLoadFailures": 4,
  "bySource": [
    {
      "source": "settings",
      "impressions": 60,
      "purchaseButtonTaps": 10,
      "successfulPurchases": 2
    }
  ]
}
```

Protect reporting endpoints with Cloudflare Access, a dashboard token, or another non-public auth mechanism. Ingestion can be public but must validate and rate-limit aggressively.

### HTML Dashboard

Add a private Cloudflare Pages dashboard at a route such as:

`https://komakode.com/debtscope/purchase-analytics`

Minimum dashboard sections:

- Paywall impressions by day.
- Paywall impressions by source.
- Purchase taps by source.
- Purchase result breakdown.
- Product load failures by day.
- Empty product responses by storefront country.
- Restore attempts and outcomes.

The HTML dashboard should call the JSON reporting endpoint and render simple tables/charts. Keep it static and dependency-light.

## iOS App Implementation

Add production analytics only after the privacy copy and App Store privacy disclosures are reviewed.

Suggested components:

- `PurchaseAnalyticsEvent`
  - Codable event model with a strict enum for event names and paywall sources.
- `PurchaseAnalyticsClient`
  - Async JSON POST client.
  - Uses `URLSession` with short timeout.
  - Silently drops events when offline or analytics is disabled.
  - Never blocks purchase, restore, import, or paywall UI.
- `PurchaseAnalyticsQueue`
  - Small local queue for retrying recent events.
  - Cap by event count and age.
  - Drop oldest events first.
- `SettingsStore.analyticsEnabled`
  - Default should be decided during privacy review. Conservative default: off until the privacy policy and App Store disclosures are ready.

Wire analytics alongside existing DEBUG diagnostics:

- Keep DEBUG local counters unchanged.
- Add production event calls in the same places as current recording hooks.
- Do not expose production analytics data in the customer-facing app.
- Do not send analytics from previews or unit tests.

## Cloudflare Worker Implementation Outline

1. Create a D1 database such as `debtscope_purchase_analytics`.
2. Add D1 binding to the Worker or Pages Functions project.
3. Add `POST /api/debtscope/purchase-events`.
4. Validate payload against strict allowlists.
5. Hash install ID with a server-side secret.
6. Insert one row into `purchase_events`.
7. Add `GET /api/debtscope/purchase-summary` behind authentication.
8. Add a minimal HTML dashboard that consumes the summary endpoint.
9. Add deploy notes to the website repo or Cloudflare Pages project docs.

## Cost Controls

- Batch client uploads only if event volume grows; start with one event per funnel action for simplicity.
- Keep payloads small.
- Keep retention limited, for example 90 or 180 days.
- Add a scheduled cleanup job to delete old rows.
- Add server-side sampling only if volume approaches free limits.
- Add an emergency kill switch in the Worker to return `{ "ok": true, "stored": false }` without writing.

## Security Controls

- Use HTTPS only.
- Reject non-POST ingestion requests.
- Validate `Content-Type: application/json`.
- Cap request body size.
- Apply Cloudflare rate limiting or Worker-side lightweight rate checks.
- Use Cloudflare Access or a secret token for dashboard/reporting routes.
- Store Worker secrets in Cloudflare environment secrets, not source control.
- Do not log raw request bodies.

## App Store And Privacy Work

Before enabling production analytics:

1. Update the privacy policy on `komakode.com`.
2. Update App Store privacy nutrition labels if required.
3. Add in-app analytics disclosure in Settings.
4. Decide default analytics state.
5. Confirm no financial content or direct identifiers are sent.
6. Validate TestFlight behavior separately from local debug behavior.

## Validation Plan

Local/unit validation:

- Event model encodes only allowed fields.
- Analytics client drops events when disabled.
- Analytics client does not block purchase flow on network failure.
- Queue caps size and drops old events.

Cloudflare validation:

- Invalid event names are rejected.
- Unknown paywall sources are rejected.
- Oversized payloads are rejected.
- Valid events insert into D1.
- Summary endpoint aggregates by source and event type correctly.
- Dashboard can render summary JSON.

Manual TestFlight validation:

- Paywall impression creates one event.
- Purchase tap creates one event.
- Cancelled purchase records `purchase_result=cancelled`.
- Successful sandbox/TestFlight purchase records `purchase_result=success`.
- Product load empty/failure records reliability events.
- Restore with no purchase records `restore_result=none_found`.
- Restore with purchased Apple ID records `restore_result=restored`.
- Turning analytics off stops new event uploads.

## Rollout Sequence

1. Build Cloudflare D1 schema and Worker endpoints.
2. Deploy private JSON reporting and HTML dashboard under `komakode.com`.
3. Add iOS event model and analytics client with user opt-out.
4. Wire purchase-funnel events behind the analytics setting.
5. Update privacy policy and App Store disclosures. Complete in `PurchaseAnalyticsPrivacyDisclosures.md`, with the user-facing Settings disclosure/toggle added under Data & Privacy.
6. Enable in TestFlight and production only after backend ingestion, privacy policy, and App Store Connect privacy answers are live.
7. Verify dashboard data against manual smoke tests.
8. Monitor production ingestion after privacy review and TestFlight validation.
9. Observe at least one release before changing price.

## Decision Criteria For Price Re-Evaluation

Do not revisit price until analytics show:

- Meaningful paywall impression volume.
- Purchase-button taps from real users.
- Product load failures are low enough that StoreKit reliability is not the main blocker.
- At least some successful purchases or clear evidence that users are rejecting the offer after seeing the value proposition.
